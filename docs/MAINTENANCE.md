## 2. 规模阈值与触发条件（按实测线性推算）

当前每条仓库约占 724 B（Brotli 259 B）。据此推算：

| 仓库数 | 索引 Brotli | 浏览器全量扫描 | 该做什么 |
|---|---|---|---|
| ~2,000 | ≈ 506 KB | ≈ 6 ms | 不用动 |
| ~4,000 | ≈ 1 MB | ≈ 13 ms | 开始预研 Web Worker 迁移（不必上线） |
| **~8,000** | **≈ 2 MB** | ≈ 26 ms | **触达 `npm test` 的 2 MiB 护栏**，必须迁移 |
| ~16,000 | ≈ 4 MB | ≈ 51 ms | 服务端检索 / 分片索引 |

按现速约 **4 年**到 2 MiB 护栏。触线前 `npm test` 会直接失败并提示迁移（见 `scripts/check-search-data.js`）。

迁移候选方案（届时按实际流量选）：
1. **Web Worker**：把 BM25 全量扫描移出主线程，索引仍静态加载 —— 改动最小；
2. **按年份分片**：`search-data-2026.json` 等按年懒加载，搜索结果按需合并；
3. **服务端检索**：Vercel Route Handler + KV/D1/OpenSearch，代价是站点不再是纯静态。

## 6. 决策记录（不要再重复研究）

### D1（2026-10-19）不引入语义向量检索

- **背景**：为「中文语义需求搜索」评估了本地向量方案（bge-small-zh-v1.5 int8 + Transformers.js + 加权 RRF，全程无外部 API）。
- **实测**（33 条中文需求评测集，同一标注）：
  | 模式 | recall@5 | MRR |
  |---|---|---|
  | 纯 BM25 | **0.866** | 0.826 |
  | BM25 + 向量 RRF | 0.851 | 0.848 |
  | 纯向量 | 0.614 | 0.657 |
  真实浏览器（headless Chrome，新 profile）：首次语义就绪约 3.8 s（模型 24 MB + wasm 传输 6.7 MB + 向量 0.4 MB），热查询约 171 ms。
- **结论**：向量通道在现有语料上没有召回收益（与 BEIR「BM25 是强基线、零样本稠密检索未必更好」一致），**不引入**；保纯前端 BM25 + 概念词表。
- **复议条件**（满足任意两条再评估）：
  1. 评测集 ≥ 50 条且 BM25 recall@5 < 0.80；
  2. 搜索日志显示大量查询落在词表覆盖之外（同义表达无法命中）；
  3. 接受「首载 30 MB+ 流量 + 浏览器端推理」的成本，或改为服务端 embedding API。
- **若重启**：优先做 cross-encoder rerank（只对 BM25 top-20），其次才是双路召回；构建期向量存 int8，查询侧用同一模型。

### D2（2026-10-19）搜索排序默认 BM25

- **理由**：在评测集上优于 RRF/纯向量；零外部依赖、首屏无额外流量。
- **替代路径**：未来若引入排序模型，只对候选集 top-20 重排，不影响首屏与索引格式。

### D3（2026-10-18）OMP 桥接超时修复（运维，不在本仓库）

- **问题**：长调研任务被 600s 超时杀掉，OMP 已产出的结果丢失。
- **修复**：`C:\Users\ACER\.agents\bin\omp-ask.mjs` 默认超时 300s → 1800s；提示词里要求 OMP 把最终答复落盘到临时文件，超时/崩溃时读该文件兜底返回。
- **注意**：这是本机工具链，不属于本仓库代码。
